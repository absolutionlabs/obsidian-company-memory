# Manual install guide — scope and size estimate

This is a SCOPE document, not the guide itself. It defines what a supplementary manual-install guide would cover, who it serves, where it sits relative to existing artefacts, and roughly how large it would be. Decision to build it lives with the operator; this doc is the input for that decision.

---

## Why a manual install guide exists

The skill is the canonical install path on Cowork and Claude Code. A small but real audience can't or won't use the skill path:

1. **Codex / opencode / other agent CLI users.** [COMPATIBILITY.md](../COMPATIBILITY.md) flags these as "compatible (not first-class)" — the scaffolded vault works fine with any agent that reads `CLAUDE.md` / `AGENTS.md`, but the skill install mechanism doesn't reach them. Manual install is the only path.
2. **Trust-conscious / regulated-sector users.** A founder in finance or healthcare may want to read every file before it touches their disk. The skill's compliance gate is the trust signal at install time; the manual guide is the trust signal at file-by-file inspection time.
3. **Air-gapped / blocked-egress users.** Corporate proxy strips `curl | sh`. Cowork plugin install rejected silently. The manual guide is the fallback when the skill bundle won't download via the canonical paths.
4. **Forkers and customisers.** [docs/customisation.md](customisation.md) covers re-packaging an edited fork. A manual install guide pairs with it — fork-then-install-by-hand becomes a single coherent procedure.
5. **Recovery operators.** When the skill fails mid-scaffold and the user deletes-and-retries unsuccessfully twice, the manual path becomes the recovery path. [docs/troubleshooting.md](troubleshooting.md) currently sends those users to `info@absolutionlabs.com`; the manual guide gives them a self-serve option first.

This is not a primary path. It's a safety net + an audit-trail artefact. The skill remains canonical.

## What the guide would cover (section breakdown)

| # | Section | Purpose | Est. lines |
|---|---|---|---|
| 0 | Preamble | When to use this (and when NOT to — point users back at the skill); audience; what you'll need; estimated time (~45-60 min) | 30-40 |
| 1 | Prerequisites checklist | Obsidian installed (link), target folder empty, ability to edit JSON/YAML by hand, terminal access for sed/PowerShell substitution | 25-35 |
| 2 | Get the bundle | `git clone` from the canonical repo (recommended) OR download zip + verify checksum. Includes the public-repo URL once it's live. | 30-40 |
| 3 | Self-check the 2 compliance items | Re-renders the skill's Step 1 gate as text the user reads and answers honestly to themselves. No checkbox UI; just the question, the answer, the "OK, continue" gate. v1.2.1 cut the third item ("Absolution Labs has no access") — the fact is now stated passively above the two checks. | 20-30 |
| 4 | Verify the target folder is empty | `ls -la` / `dir` invocation; what to ignore (`.DS_Store`, `Thumbs.db`, `desktop.ini`); what to do if not empty | 15-20 |
| 5 | Substitution variables | The 5 placeholders + how to pick values + an OS-by-OS substitution recipe (sed on macOS/Linux, PowerShell on Windows). Includes the four scope-exception rules from SKILL.md Step 6 ("substitute these in THIS file but not in THESE files") rendered as a clear table. **This is the trickiest section** because the carve-outs are non-obvious and bugs from missing them have shipped in past sessions. | 70-100 |
| 6 | Folder structure to create | `mkdir` invocations (or copy-paste tree); the 12-folder structure from SKILL.md Substep 6.1 | 15-20 |
| 7 | File-by-file copy and substitute | A walk through every file the skill writes, in the same order. For each: source path in the bundle, destination in the vault, substitution rules (referencing § 5), brief why-this-file. ~22 files at ~3-5 lines each. | 100-150 |
| 8 | Round-trip test (manual version) | Recreate `entities/test-welcome.md` from the template; manually update `index.md`; manually append the second `log.md` entry. Same 5-step Obsidian verification as SKILL.md Substep 7.4. | 50-70 |
| 9 | Telemetry — manual choice | How to send the install-success ping by hand if you want to (curl invocation with the JSON body); how to NOT send it; how the UUID gets generated by hand. Most users will skip — this is for completeness. | 30-50 |
| 10 | Install the two custom skills in your AI tool | Walk through `_meta/skill-prompts/README.md`; install `new-project-setup` and `close-session` per surface (Cowork / Code / Codex / opencode). Most of this is "read the file the bundle ships" not new content. | 40-50 |
| 11 | Verification checklist | What the finished vault should contain (file tree); what should parse (markdown / YAML / JSON); what wikilinks should resolve | 30-40 |
| 12 | Common manual-install mistakes | A focused subset of [troubleshooting.md](troubleshooting.md) for the manual path specifically: forgetting one `.template` file, substituting in the wrong file per the carve-outs, copying `.obsidian/` JSON with literal `{{COMPANY_NAME}}` (no substitution there), pasting into the wrong vault path | 40-60 |
| 13 | Upgrading a manually-installed vault | Pointer to [docs/upgrading.md](upgrading.md) + the specific differences for manual installs (no scaffold-version.txt write-back unless you do it; how to bump it manually if you upgrade) | 25-35 |
| 14 | When to switch to the skill | "You've installed manually; now you have Cowork or Claude Code working. Should you re-install via the skill?" Short answer: no, your vault is fine. Long answer: you can if you want symmetry with future upgrades, but it requires the empty-folder dance. | 20-30 |

### Estimated total

**Lines:** ~520 – 770. Tight, focused writing lands closer to the lower end; a friendly tone with worked examples lands closer to the upper end.

**Words:** ~3,500 – 5,500.

**Reading time:** ~15-25 minutes for a careful reader who is following along on disk; ~5 minutes for a skim before deciding "yes, this is the path for me."

**Active install time** following the guide: ~45-60 minutes vs ~25 minutes via the skill. The slowdown comes mostly from § 5 (substitution recipes) and § 7 (file-by-file walk).

## What this guide would NOT cover

- **Migration from an existing vault.** Same exclusion as the skill (key decision #14). Refusing is the safe answer for the skill; the manual path inherits that refusal as a "do not pour the bundle on top of an existing folder."
- **A fully-scripted bash/PowerShell installer.** That would be a third install path (`./install.sh`-style) and a different artefact. Out of scope here; potential follow-up if the manual guide gets enough traction to justify it.
- **Multi-platform GUI installer.** Same — different artefact.
- **Differences for `.obsidian/` versions older than 1.5.** Already declared unsupported in [COMPATIBILITY.md](../COMPATIBILITY.md).
- **In-vault editing of the substitution result.** Once the files are on disk, the rest of the docs (HOW-TO-USE-THIS.md, customisation.md) take over. The manual install guide stops at "round-trip verified."

## Risks and gotchas the guide must address

These are the things most likely to bite a manual installer; the guide must call each out explicitly:

1. **Substitution scope exceptions** (SKILL.md Step 6's four carve-out rules). Bugs from missing these have already shipped in the skill path; in the manual path they would be even easier to miss. § 5 + § 7 cover this; the **`.template` files in particular** must NOT have substitution applied — they go to disk with placeholders intact, for `new-project-setup` to consume later.
2. **`.obsidian/` JSON files** carry no `{{COMPANY_NAME}}` placeholders. The manual installer might run sed over the whole `templates/` folder and discover nothing changed; that's correct, not a failure.
3. **`{{TODAY}}` in `_meta/templates/*.md`** must NOT be substituted (they're user-copy templates the user clones at page-creation time months later; baking the install date defeats lint stale-page detection).
4. **`scaffold-version.txt`** is built fresh at runtime, not from a template. The guide gives the exact 6-line content to write.
5. **`log.md` second entry** is post round-trip, not pre. The user MUST run the 5-step Obsidian verification before adding the "round-trip passed" entry to `log.md`. § 8 enforces this ordering.
6. **The skill-prompts handoff.** The `_meta/skill-prompts/` files are NOT optional; they are how the user installs the two custom skills (`new-project-setup`, `close-session`) into their AI tool. § 10 makes this front-and-centre.

## Decision aids for whether to build it

**Build it if:**
- Any tester in the private beta says "I want to read every file before installing" or "the install script wouldn't run on my machine."
- Codex / opencode adoption among prospects shows up in feedback.
- A regulated-sector prospect signals that the skill path itself is a compliance blocker (uncommon but possible).

**Defer or skip if:**
- Private beta + first 30 days post-public-ship show zero manual-install requests.
- The Cowork + Code install paths have ≥95% success rate (the skill's stated Impact Metric).
- The team's attention is needed elsewhere on `release/` work (test matrix, Recovery Drill, etc.).

**Estimated build time** (per OP #16 calibrated for multi-block autonomous AI work):
- Single-block stated AI-time budget: ~3-4 hours.
- Actual wall-clock if built autonomously: ~30-45 minutes.
- This is a one-shot doc, no live infra, no smoke tests required beyond a self-install dry-run. Low blast radius.

## Open questions for the operator

1. **Hosting.** Does the manual guide live in `docs/` (bundle-internal) or also at `absolutionlabs.com/obsidian/manual` (publicly-discoverable)? Recommendation: bundle-internal only for v1; if it gets traction, surface on the install page in v1.1.
2. **Versioning.** When the skill version bumps (v1.0 → v1.1), the manual guide must bump with it. Cadence: same as `docs/upgrading.md` — quarterly review minimum, immediately on any skill version that changes file content.
3. **Skill vs manual divergence.** If the skill grows a new step (e.g. a future "what color theme do you want?" question), the manual guide must mirror it. This adds a maintenance tax. Worth tracking via [MANIFESTS.md](../MANIFESTS.md) mirror-contract pattern — extend the lint to also check parity between SKILL.md procedure and manual-install-guide.md steps.

---

## Recommendation

Build it post private beta, before public ship — only if at least one of the trigger conditions above fires. Otherwise defer to v1.1 as an "add-if-asked" item in [post-launch-backlog.md](../release/post-launch-backlog.md).

Reasoning: the manual path is real but quiet. Building it pre-emptively adds ~520-770 lines of artefact the operator now has to maintain forever; building it on demand keeps the trust artefact lean and lets the actual ask shape the scope. The 30-45 min build cost is small enough that "wait for the ask" is cheap insurance against premature doc-bloat.
